# Password recovery (P1-15)

SchoolERP uses the standard ASP.NET Core Identity password-reset token provider. Tokens are protected by ASP.NET Core Data Protection, have a configured one-hour lifetime, are never persisted in a reset-token table, and are Base64Url-encoded before being placed in a frontend link.

```text
Forgot Password
   |
   v
Generic API Response
   |
   +-- account exists and is eligible?
         |
         v
Generate Identity Reset Token
         |
         v
Send Reset Link

Reset Password
   |
   v
Validate Token
   |
   v
Reset Password
   |
   +--> Update PasswordChangedAt
   +--> Update SecurityStamp
   +--> Clear Lockout and access failures
   +--> Revoke Refresh Sessions
   |
   v
Require Normal Login
```

## Forgot-password behavior

`POST /api/v1/auth/forgot-password` accepts an email address and always returns HTTP `202` with the same message for well-formed known and unknown addresses:

> If an account exists for this email, password reset instructions have been sent.

This prevents direct account enumeration. Active, pending, locked, and suspended users may receive recovery mail. Deactivated users do not receive mail, but receive the identical public response. Tenant, school, and campus operational state is intentionally not checked during recovery.

The endpoint is limited to five requests per 15 minutes per IP. Delivery failures are logged without the link or token and do not change the public response.

## Reset behavior

`POST /api/v1/auth/reset-password` accepts email, encoded token, new password, and confirmation. Malformed, expired, consumed, unknown-user, and deactivated-user requests receive the same safe invalid/expired response. The endpoint is limited to ten requests per 15 minutes per IP.

Password strength is enforced by the existing Identity policy. Safe policy descriptions may be returned, but Identity internals are not exposed. Successful reset:

1. Calls `UserManager.ResetPasswordAsync`; password hashes are never assigned directly.
2. Records `PasswordChangedAt` in UTC and explicitly updates the security stamp.
3. Clears temporary Identity lockout and failed-access count.
4. Revokes every refresh-token session with reason `PasswordReset`.
5. Returns no access token, refresh token, reset token, or security stamp. The user must log in normally.

Identity security-stamp changes make a successfully consumed token, and other tokens issued against the former security state, unusable. Suspended or pending status is preserved; recovery never activates or confirms an account. Deactivated accounts are rejected generically.

Password update and session cleanup are separate Identity/session operations rather than a claimed distributed atomic unit. If security-state or session cleanup fails after password modification, the API returns a safe `500` and records a critical security event for operational remediation; it never attempts to restore the old password.

## Email and URL handling

`IEmailService` isolates the recovery workflow from providers. The current infrastructure implementation uses configured SMTP and sends a plain-text message titled `Reset your SchoolERP password`, including expiry and ignore-if-unrequested guidance. Tests replace it with an in-memory fake.

Links use `Frontend:BaseUrl` and `/reset-password?email=...&token=...`. Both values are URL encoded. The frontend reset page should use `Referrer-Policy`, avoid third-party analytics/trackers, remove the token from the visible URL after capture, and use `autocomplete="new-password"` for password fields.

## Configuration and deployment

```json
{
  "PasswordReset": { "TokenLifespanMinutes": 60 },
  "Frontend": { "BaseUrl": "https://app.schoolerp.example" }
}
```

Token lifespan must be between 5 minutes and 24 hours, and the frontend URL must be absolute HTTP(S). Production SMTP credentials belong in a secret store, not configuration files.

Data Protection defaults are suitable for one development API instance. Multiple production instances must share and persist Data Protection keys—for example through a database, shared filesystem, Redis, or cloud key store—otherwise a token generated by one instance may fail on another. P1-15 does not select or provision that deployment-specific store.

## Access-token limitation and auditing

Password reset immediately prevents old refresh sessions from extending authentication. Existing stateless JWT access tokens may remain valid until their short expiration; no JWT blacklist or per-request security-stamp lookup was added.

Structured logs cover reset requests, mail delivery outcome, invalid tokens, successful resets, failures, and session revocation. Logs include user ID when known and request IP, but never request DTOs, reset links, reset tokens, passwords, or password hashes.
